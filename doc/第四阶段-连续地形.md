# 第四阶段：连续地形调研

本文件记录第四阶段"连续地形原型"的技术可行性调研结论，供后续轮次实现时参考。

调研日期：2026-08-10。调研基于仓库内 `references/RimWorldDecompiled/`（1.6 / Odyssey 时代反编译源码）。

> **架构状态（2026-08 重构后）**：本文 E 节描述的接缝覆写卷积混合（dSq/(dSq+dHex) 权重、wCap、A 全图候选枚举、单层地形混合）已被**接缝带定义重构**整体取代——现行架构（3 圈接缝带、连续边中点对齐 offset、三层条带快照 terrain/building/roof、B_C 照抄 + T_C 源地图轴卷积）的权威定义见 [接缝带定义](接缝带定义.md)。本文保留作调研与实现历程记录，其中接缝混合的具体机制描述均以新文档为准。

## 总览

第四阶段原定义是"连续地形原型"——让相邻地块在接缝处共享高度/地形/河流/道路/水域。经深入调研，连续地形的完整实现需要重写原版基于 tile 种子的 noise 管线，工作量大且分项可行性差异显著。本轮聚焦**调研 + 两个可直接落地的实现项**（边界带不可建造约束 + 共因 bug 修复），连续地形四项分轮推进。

## A. 异步加载可行性

### 背景

地图生成（`MapGenerator.GenerateMap`）是重操作。在游戏运行中生成口袋地图（pawn 接近边界预加载）时，之前尝试异步加载多次失败，最终采用 `LongEventHandler.QueueLongEvent(doAsynchronously:true)`（显示进度画面、ForcePause 几秒）。

### 之前失败方案及根因

| 方案 | 失败根因 |
|---|---|
| 纯 Thread（无进度画面）| `List<Map>.Add` 与主线程 foreach `Find.Maps`（ColonistBar/Alerts 每帧枚举）的 `_version` 竞争 → `InvalidOperationException` |
| 拆分式异步（主线程 AddMap → 工作线程 genSteps → 主线程 FinalizeInit）| AddMap 后 map 进 `Find.Maps`，主线程 `TickManager` 每 tick 调 `map.MapPostTick` → `tempTerrain.Tick` → `GetRoom` → `GetValidRegionAt`，region 空时刷海量 "RegionAndRoomUpdater is disabled" warning + 寻路失效（pawn 卡接缝）|

### MapGenerator.GenerateMap 执行序列（`Verse/MapGenerator.cs:79-232`）

关键时序：第 146 行 `AddMap` → 第 186 行 `genSteps` → 第 190 行 `FinalizeInit`，三者必须在主线程恢复 tick 前连续完成。

| 步骤 | 行号 | Unity API | 纯数据 | 改全局 |
|---|---|---|---|---|
| `ProgramState = MapInitializing` | 82 | 否 | 是 | 是 |
| `mapBeingGenerated = map`（静态槽）| 114 | 否 | 是 | 是 |
| `map.ConstructComponents()` | 140 | 否 | 是 | 否 |
| `Current.Game.AddMap(map)` | **146** | 否 | 否 | **★** |
| `extraInitBeforeContentGen`（RimExodus 的 InjectRealTileInfo）| 154 | 取决回调 | 多数 | — |
| `GenerateContentsIntoMap(genSteps)` | **186** | 混合 | — | **★** |
| `map.FinalizeInit()` | **190** | 部分 | — | **★ 启用 region/pathing** |

### 子类化方案（用户原思路）：不可行

`Verse/Map.cs:13`：
```csharp
public sealed class Map : IIncidentTarget, ILoadReferenceable, IThingHolder, IExposable, IDisposable
```

`Map` 是 `sealed`，C# 编译期禁止继承，Harmony 也绕不过。这是不可逾越的障碍。

### 新方向：延迟 AddMap 方案（实验验证后已被更优方案取代）

**核心洞察**：根因不是"某个 API 必须 main thread"，而是"map 一旦 AddMap 进入 `Find.Maps`，主线程每帧 foreach `Find.Maps` 的系统就会访问半成品 map 崩溃"。如果能延迟 AddMap 到 FinalizeInit 完成后，生成期间 map 不在 `Find.Maps`，所有入口（TickManager/Alerts/ColonistBar/MapUpdate/Storyteller/渲染）天然全跳过它。

**实验分支（`experiment/deferred-addmap-async`）验证结论**：延迟 AddMap 方案理论上可行（已实现 sentinel + ConditionalWeakTable + 5 patch 的完整原型，编译通过），但深入审查暴露了两个层面的障碍：

**障碍 A（可修复的实现 bug，已修复）**：
- TickManager Prefix 用 ConditionalWeakTable 判断时机太晚（Postfix 才注册）→ 改用 `IsSentinel(mapIndexOrState)`
- FinalizeHalfBaked 移除 halfBakedMaps 时机太早（MapGeneratorPostInit 还会 spawn）→ 推迟到 GenerateMap 完全返回
- ConditionalWeakTable 孤儿条目导致 finalize 窗口 getter 错乱 → 逐个 Remove

**障碍 B（根本性 static 竞争，致命）**：
- `Rand`（`Verse/Rand.cs:14-20`）的 `seed`/`iterations`/`stateStack` 是**普通 static 非 ThreadStatic**。工作线程跑 `MapGenerator.GenerateMap` 的 `Rand.PushState/Seed/PopState` 与主线程 tick 的 Rand 使用竞争 → 主线程 `stateStack` 弹空栈崩溃。
- `MapGenerator`（`Verse/MapGenerator.cs:12-30`）的 `mapBeingGenerated`/`data`/`tmpGenSteps` 等 static 同样被工作线程独占，主线程读到工作线程的值。
- **这是"纯后台 Thread 跑原版 GenerateMap"的固有障碍**，与延迟 AddMap 无关。RimWorld 原生用 `LongEventHandler(doAsynchronously:true)` 时，ForcePause 暂停主线程 tick（不是暂停线程，而是主线程在 LongEventHandler 轮询循环里等待，不再调 `DoSingleTick`），所以工作线程独占 static 期间主线程不碰它们。纯 `new Thread` 没有 ForcePause，主线程继续 tick，竞争就发生。

### 突破：`forceHideUI` 方案（最终结论）

深入调研 `LongEventHandler` 发现**原版自带的 `forceHideUI` 开关完美解决所有问题**：

```csharp
LongEventHandler.QueueLongEvent(action, null, doAsynchronously: true,
    exceptionHandler, showExtraUIInfo: false, forceHideUI: true);
```

机制（`Verse/LongEventHandler.cs`）：
- `forceHideUI=true`（:38, :151）→ `LongEventsOnGUI`（:200-203）直接 return，**不画进度画面**。
- `doAsynchronously=true` → `ShouldWaitForEvent=true`（:99-103，因 `UseStandardWindow=false`）→ `Root_Play.Update`（:63-66）跳过 `UpdatePlay`（含 `TickManagerUpdate` 和 `MapUpdate`）。
- `ForcePause=true`（:138 = `AnyEventNowOrWaiting`）→ `TickManager.ForcePaused`（TickManager.cs:146）→ `TickManagerUpdate`（:321 `if (Paused) return`）。
- 异步路径不 `thread.Join`（:364-405），主线程不阻塞，**渲染继续**，玩家看到当前游戏画面。

**三重保护**：tick 暂停（不碰 Rand/MapGenerator static）+ UpdatePlay 跳过（不 MapUpdate、不渲染半成品 map）+ forceHideUI（不画进度画面）。工作线程独占跑 GenerateMap，无竞争、无崩溃、玩家无感。

**结论**：延迟 AddMap 机制（sentinel + ConditionalWeakTable + 5 patch）完全不需要——`forceHideUI` 是原版为"隐藏 UI 的 long event"设计的标准开关，一行参数解决所有问题。实验分支验证了延迟 AddMap 方案的可行性边界，但最终采纳 `forceHideUI` 方案。

### 当前方案（forceHideUI）评估
- RimWorld 原生自己都做不到无进度画面——`SettleInEmptyTileUtility`（玩家游戏运行中建立新基地）同样用 `doAsynchronously:true` 但**没有 forceHideUI**，所以显示进度画面。RimExodus 用 `forceHideUI=true` 比原生更进一步。
- 代价：ForcePause 期间玩家无法操作（但可看画面、移动视角）。生成只需几秒，体验远好于进度画面闪烁。
- 这是当前能实现"无进度画面"的最优方案。纯后台异步（不中断操作）仍需 fork Rand/MapGenerator 改 ThreadStatic（fork 级工作量，不推荐）。

### 更优方案：分帧增量生成（`IncrementalMapGenerator`，实验分支已实现）

forceHideUI 仍需 ForcePause（玩家无法操作几秒）。要做到**完全不暂停 tick、玩家全程可操作**，可行路径是**分帧增量生成**：主线程每帧跑 1-2 个 genStep，N 帧完成，每帧只比正常 tick 多花几~几十 ms。

#### 可行性依据（调研确认）
- **genStep 间 Rand 状态独立**（`MapGenerator.cs:317-335`）：每个 genStep 开始时 `Rand.Seed = Gen.HashCombineInt(baseSeed, GetSeedPart(index))` 完全重置，`GetSeedPart`（:439-451）是纯函数（只依赖 SeedPart + 列表位置），不依赖前一 genStep 的 Rand 末状态。主帧 tick 期间改变 Rand 不影响下一个 genStep。
- **genStep 间共享数据通过 MapGenerator static 保持**（`tmpGenSteps`/`data`/`mapBeingGenerated`/`RockNoises`），分帧期间不 `ClearWorkingData`/`Reset`。
- **原生 `DebugDoNextGenStep`（:234-262）已证明跨帧逐 genStep 执行合法**——它是用户驱动的调试生成器，跨帧跨用户操作，结果与一次性生成一致。
- **FinalizeInit 单帧执行**（:801-856），`RebuildAllRegionsAndRooms` 不能拆——保留最后一段卡顿（~100-300ms），可接受。

#### 最小实现（无需延迟 AddMap，无需 Rand 隔离）
- map 正常 `AddMap`（让 `Thing.SpawnSetup:819` 的 IndexOf 通过，spawn 正常）。
- 给 map 加 `generating` 标志，patch **3 个 Map 方法**让 generating map 早退：
  - `Map.MapPreTick`（`Map.cs:933`）—— 跳过 tick
  - `Map.MapPostTick`（`Map.cs:966`）—— 跳过 tick
  - `Map.MapUpdate`（`Map.cs:1148`）—— 跳过渲染更新（避免渲染半成品 map）
- 复刻 `GenerateContentsIntoMap:317-345` 循环，每帧跑 1 genStep（`Rand.PushState/Seed/Generate/PopState`）。
- 全程主线程，无 Rand/MapGenerator static 竞争（因为是顺序执行，不是并发）。

#### 已知风险（实验性，待游戏内验证）
- **全局 TickList 会 tick 到 generating map 上的 Thing**：`RegisterAllTickAbilityFor` 是全局的，genStep spawn 的 Thing（动物/植物）会进 TickList 被 tick。岩石/植物 tick 只生长（无害），动物 AI 在 region 未建时寻路失败但不崩。若实测有问题，patch `TickList.Tick` 过滤 generating map 的 Thing。
- **`mapBeingGenerated` 分帧期间保持非 null**：主线程其他 map 的 tick（`WildAnimalSpawner:115`/`PollutionGrid:94`）读到它，可能轻微抑制动物刷新/污染通知。行为层面影响，非崩溃，只持续几秒。
- **不翻转 `ProgramState`**（保持 Playing）：原版 GenerateMap 设 `MapInitializing`，但分帧期间主线程 tick 读到它会导致 20+ 处守卫逻辑错乱。实验性保持 Playing，若 genStep 依赖 MapInitializing 再调整。
- **`FinalizeInit` 单帧卡顿**：~100-300ms，是分帧方案留下的最后一段卡顿。若需进一步优化，可拆 `Thing.PostMapInit` 循环为多帧（v2）。

#### 实现文件（实验分支 `experiment/deferred-addmap-async`）
- `Source/IncrementalMapGenerator.cs` — 分帧生成器 MapComponent（准备阶段 + genStep 分帧 + FinishGeneration）
- `Source/Patches_IncrementalMapGen.cs` — patch Map.MapPreTick/MapPostTick/MapUpdate 早退
- `Source/SeamlessTileManager.cs` — `GenerateTileMap` 改用 `IncrementalMapGenerator.Start`，后续配置放 `onComplete` 回调

### 最终实现状态（已验证完成）

分帧增量生成方案已在实验分支 `experiment/deferred-addmap-async` 完成验证：**无进度画面、不暂停 tick、无红字/NRE、性能良好**。玩家在生成期间可继续操作其他地图。

#### 核心组件

1. **分帧生成器 `IncrementalMapGenerator`**（`Source/IncrementalMapGenerator.cs`）
   - `MapComponent`，主线程每帧跑 1+ genStep（时间预算 `TimeBudgetMs=8ms`），N 帧完成。
   - 准备阶段（`ConstructComponents`→`AddMap`→组装 genSteps）同步完成，genStep 链分帧执行，`FinalizeInit` 单帧执行。
   - `IsGenerating(map)` 供 patch 判断 generating map 早退；`IsAnyGenerating` 供外部判断。

2. **Generating map 早退 patch**（`Source/Patches_IncrementalMapGen.cs`）
   - `Map.MapPreTick` / `Map.MapPostTick`：generating map 跳过 tick。
   - `Map.MapUpdate`：generating map 跳过渲染更新（避免渲染半成品 map）。
   - 玩家可继续操作其他 map，generating map 静默等待分帧完成。

3. **void 内嵌 Terrain genStep**（`1.6/Defs/MapGeneration/SeamlessTileGenerator.xml`）
   - `RimExodus_SeamlessTile` genStep `order=1400`（初版为 211：Terrain(210) 之后、Plants 之前；后移原因见 E.6 与 doc/地图生成步骤.md——snapshot 备份须在 Settlement(400) 等写 topGrid 的步骤之后，且让 Fog(1500) 基于裁切后地形揭雾）。
   - 备份 snapshot 后把多边形外格覆写为 void。后移到 1400 后 Plants(900)/Animals(1200) 已 spawn，void 格上的实体由 `ClearThingsOnCells`/`EvacuatePawnsOnCells` 事后清理（岩石由 order=200 patch 预清），"后续 genStep 读 terrainGrid 自然不 spawn"只在初版 211 时序下成立。

4. **RocksFromGrid Postfix 清 void 格岩石**（`Source/Patches_GenStepRocksFromGrid.cs`）
   - `order~200`（RocksFromGrid 之后立即），清掉 void 格上的岩石 + 屋顶，避免落石。
   - 使 `RimExodus_SeamlessTile`（现 order=1400）的 `ClearThingsOnCells` 无需处理岩石 Building（初版 order=211 时为完全空操作，后移后主要清理植物/物品）；锚点地图的 void 也走同一条 genStep 链（通过 XML patch 注入到 Base_Player），不再有独立的 `RefreshMapVoid` 后补路径（该方法已删除）。

5. **Plants 分帧**（`IncrementalMapGenerator.SubStepState` + `RunSubStepChunk`）
   - Plants 是最重的 genStep（250×250 地图约 62500 格），单帧跑会卡 ~8000ms。
   - 拆成每批 2000 cells，每帧跑到时间预算耗尽，独立 `Rand.Seed` per batch（`Gen.HashCombineInt(state.randSeed, batchIndex)`），保证跨帧 Rand 独立、可复现。
   - 每帧 Plants 处理 <50ms。

6. **ApplyPolygonTerrain 直接写 topGrid**（`Source/SeamlessTerrainFill.cs`）
   - 跳过 `SetTerrain` 的 `DoTerrainChangedEffects`（pathGrid/waterBodyTracker 重算，21000 次 × 副作用 = 5.7 秒），直接写 `terrainGrid.topGrid` + `MapMeshDirty(Terrain, regenAdjacentCells:false, regenAdjacentSections:false)`。
   - pathGrid 由 `FinalizeInit` 全量重算覆盖；mesh 由 `RegenerateEverythingNow` 全量重建。

7. **ProgramState 翻转**（`IncrementalMapGenerator.RunOneGenStep`）
   - genStep 执行期间临时设 `ProgramState=MapInitializing`（原版 `GenerateMap:82` 行为），genStep 结束后恢复 `Playing`（主线程 tick 在 genStep 之间发生，那时 ProgramState 已恢复）。
   - 修复 `WaterBodyTracker.Notify_TerrainChanged`（:175 检查 `ProgramState==Playing` 才执行）在生成期间触发 `TryCreateBodyOrAddToExisting` → NRE（bodies 未初始化）。

8. **Rand.Seed PushState/PopState 保护**（`IncrementalMapGenerator` 准备阶段 + `RunOneGenStep` + `RunSubStepChunk`）
   - `Rand.Seed` setter 要求 `stateStack.Count > 0`，每个 seed 设置都 `PushState/Seed/PopState` 配对。
   - 不保持外层 Rand 栈帧——`Root.Update` 每帧调 `EnsureStateStackEmpty` 会清空跨帧保持的栈，导致后续 `PopState` 弹空栈。
   - 消除 "Modifying initial rand seed" 红字。

#### 性能数据
- **RimExodus_SeamlessTile（void 裁切）**：5762ms → 30ms（直接写 topGrid + MapMeshDirty 替代 SetTerrain 副作用）。
- **Plants genStep**：8000ms（单帧卡顿）→ 分帧每帧 <50ms。
- **总生成**：无单帧卡顿，每帧 genStep 时间预算 8ms，剩余时间给 tick/渲染。
- **移除 `FinishGeneration` 里对锚点 map 的冗余 `RefreshMapVoid`**：原每次生成邻居都重铺锚点 void，清掉玩家游戏期间生长的植物/掉落物，耗时 12-23 秒。改为 void 只看自己的多边形（不因邻居关系变化而变），开档时 `TrySetupOnStart` 铺一次即可。

#### 最终结论
分帧增量生成是当前能实现"无进度画面、不暂停 tick、无红字 NRE"的最优方案。纯后台异步（不中断操作 + 工作线程并发）受 Rand/MapGenerator static 非 ThreadStatic 限制不可行（需 fork 级工作量改 ThreadStatic），分帧方案在主线程顺序执行天然避免 static 竞争。

### 当前方案（LongEventHandler）评估

RimWorld 原生自己都做不到无进度画面——`SettleInEmptyTileUtility`（玩家游戏运行中建立新基地）同样用 `doAsynchronously:true` + ForcePause。这是 Ludeon 自己的设计选择。

正确优化方向：缩短单次生成耗时（缩小地块尺寸、减少 genSteps、异步预生成 noise/地形数据但不调 GenerateMap），而非分帧执行 GenerateMap。

## B. 连续地形四项可行性分级

### 共因 bug（已修复）

> **架构变更说明**：本节描述的 bug 发生在早期 PocketMap 架构下（当时 `mapParent.Tile = 0`）。当前基础地图架构下 `mapParent.Tile = 真实 PlanetTile`，`map.TileInfo` 自动读 `Find.WorldGrid[Tile]`（含真实 biome/hillness/mutators/rivers），此 bug 已从根源消除。下文保留原始调研记录。

`SeamlessTileManager.GenerateTileMap:269` 设 `mapParent.Tile = 0`（旧口袋地图惯例，VMF 也如此）。

后果：
- `RockNoises.Init`（`Verse/RockNoises.cs:22`）用 `map.Tile` 调 `NaturalRockTypesIn(map.Tile)`（以 `tile.GetHashCode()` 为 seed 选岩石类型集合）→ 所有地块地图读到 tile 0 的岩石类型。
- `GenStep_Roads.CalculateNeededRoads`（`:113`）用 `map.Tile` 读道路数据 → 读不到真实道路。
- `map.TileInfo.Mutators` 为空 → 河流 mutator 根本没跑。

**当时修复**：Prefix patch `RockNoises.Init`，对 RimExodus 地块地图用 `MapParent_SeamlessTile.worldTile` 查岩石类型。当前架构下该 patch 已不需要（Tile 是真实值），但 `Patches_RockNoises.cs` 已在后续重构中删除。

### 1. 高度/地形对齐：完全可做

**核心机制**：`GenStep_ElevationFertility`（`RimWorld/GenStep_ElevationFertility.cs:35-96`）用 Perlin 噪声写 `MapGenerator.Elevation`/`Fertility` grid。Perlin seed（`Verse.Noise/Perlin.cs:148`）只是哈希系数：

```csharp
// Utils.cs:176-188 GradientNoise3D
long num = (1619 * ix + 31337 * iy + 6971 * iz + 1013 * seed) & 0xFFFFFFFFu;
num ^= num >> 8; num &= 0xFF;
double num2 = _randoms[num << 2]; // 查 1024 常量表
```

**没有置换表**。seed 只是整数乘法系数，`GetValue(x,y,z,seed)` 是纯函数。给定相同 seed 和相同坐标，输出逐位一致。

**随机源全需确定化**（不止 seed，还有频率/缩放/旋转）：
- `:49` Elevation Perlin seed + 频率
- `:51-57` detail/warp displacement 的频率/强度/层数/seed（`MapNoiseUtility.AddDisplacementNoise`）
- `:53-57` pre/post turbulence stretch + 旋转角
- `:88` fertility Perlin seed

**推荐 patch 策略**：预填 grid + Prefix 跳过原 GenStep。
1. 在 `extraInitBeforeContentGen` 回调（RimExodus 已用此回调注入 TileInfo）里，用世界坐标确定性 Perlin 预填 `MapGenerator.Elevation`/`Fertility` grid（`FloatGridNamed` 是 get-or-create 语义，预填值会被存进 `data` 字典）。
2. Prefix patch `GenStep_ElevationFertility.Generate`，检测 grid 已预填则 `return false`（跳过原方法）。
3. `GenStep_Terrain`（纯函数，读 grid）、`GenStep_RocksFromGrid`（读 grid）自动用预填值。

**世界坐标构造**：每个 pocket map 的 cell (x,z) 映射到世界绝对坐标 = 该 tile 的世界锚点 + cell 偏移。接缝两端 cell 的世界坐标对齐由现有 `NeighborLink.offset` 提供。

**优势**：避免重写整个 elevation/fertility 逻辑（只写"世界坐标采样"那一小段），不用 Transpiler（脆弱），可控可回退。

### 2. 岩石类型对齐：完全可做

`RockNoises.Init`（`Verse/RockNoises.cs:19-30`）的 Perlin 也是纯函数（同 Perlin 机制）。`GenStep_RocksFromGrid.RockDefAt`（`:26-46`）遍历 `rockNoises` 取 `noise.GetValue(c)` 最大的 rockDef，纯函数无随机。

**推荐 patch 策略**：Prefix `RockNoises.Init`（本轮已部分修复——用真实 worldTile 查岩石类型）。连续化进一步：seed 用 `Gen.HashCombineInt(WorldSeed, worldTile, rockDef.shortHash)` + 世界坐标采样。

### 3. 河流对齐：部分能做

**生成机制**（`RimWorld/TileMutatorWorker_River.cs`，是 TileMutator 非 GenStep）：
- `GenerateRiverGraph`（`:141-169`）：读 tile 的 `Rivers` 列表（`SurfaceTile.potentialRivers`），按邻居 `riverDist` 排序，`GetHeadingFromTo` 算流向角，`GetMapEdgeNodes`（`GenGeo.LineRectIntersection`，纯几何）求入出点。
- `Init`（`:71-86`）：4 个 `Rand.Int` seed 构造 `riverBendNoise`/`shallowizer`/`riverbankNoise`/`riverWidthNoise`。
- `GetDisplacedPoint`（`:253-263`）：弯曲 noise 采样输入是 `num2 = t × 河段长度`（**局部弧长**，非世界坐标）。

**可做部分**：
- 入出点 + 宽度 + 接缝穿越点：几何确定化。Prefix `GenerateRiverGraph` 用接缝锚点覆盖 `riverCenter`；`width = riverDef.widthOnMap` 两端天然一致（`WorldGrid.OverlayRiver` 对称写入同一 RiverDef）。
- 接缝处"看起来连上"：两端在边缘都直（`num = -4t²+4t` 抛物线包络在 t=0/1 处为 0，强制边缘直），宽度相同，视觉连续。

**不能做部分**：
- 接缝带宽以外两端弯曲重合：`riverBendNoise` 是局部弧长驱动，两端河段长度/起点不同，即使 seed 相同弯曲偏移不同。`RiverCurveAmplitude=40` 格幅度很大，远离接缝两端各自弯曲。

**先决条件（当前架构已部分满足）**：基础地图架构下 `map.TileInfo` 自动读真实 WorldGrid 数据（含 Mutators），River mutator 会正常执行。早期 PocketMap 架构下 Mutators 列表为空且 `pocketTileInfo` 是基础 `Tile` 类（非 `SurfaceTile`），该问题已随架构迁移消除。

**推荐 patch 策略**：Prefix `TileMutatorWorker_River.GenerateRiverGraph`（只 patch River 及子类，不影响其他 mutator）。

### 4. 道路对齐：穿越点对齐（已实现）

**生成机制**（`RimWorld/GenStep_Roads.cs`，order=390）：
- `FindRoadExitCell`（`:149-193`）：`CellFinder.TryFindRandomEdgeCellWith` 随机选边缘 cell（依赖 `reachability.CanReach`）。
- `PrepDrawRoad`（`:201-245`）：`map.pathFinder.FindPathNow` **A* 寻路**（强依赖整图通行成本网格）+ Bezier 平滑 + 距离场。
- `ApplyDistanceField`（`:330-358`）：`Rand.Value` 概率放置路面/边石。

**根因**：`GenStep_Roads`(390) 在 void 铺设(1400) **之前**执行，此时传送点不存在 → `HasSeamEdge` 返回 false → `Patches_CellFinder` 放行原版方形边缘 → 道路出口格选在方形边缘（将来多为 void）→ 被 void 覆盖 + 两端不对齐。

**已实现方案**：Patch `GenStep_Roads.FindRoadExitCell`（private，`Source/Patches_GenStepRoads.cs`），Prefix 用多边形几何算目标角度对应边的接缝锚点格作为出口。**边匹配用权威邻居身份映射**（`FindRoadLinkEdgeByHeading`，只遍历有 road link 的邻居）——原版 `CalculateNeededRoads` 对多条路的 angle 加向量平均偏置+随机抖动（让方形边缘出口散开），两条路夹角 60° 时偏置可达 60° 直接错到隔壁邻居边；被污染的 angle 不能信任，过滤到 road 邻居后偏置再大也命中正确 link。两端各自算自己在该边的锚点，通过 offset 对齐。道路 A* 寻路到锚点 → 道路画到接缝带 → void 只覆盖六边形外（接缝带在内不受影响）→ SeamOverride 的道路保护（IsRoad/bridge 地形判据 + paths±3 缓冲）保留路面。

**道路与河流的交互（绕行问题，已修复）**：河端点若停在六边形边中点，河源头后方（边中点到方形边 ~15-40 格）出现无水走廊（岩石已被 order 200 patch 清掉、void 1400 才铺）——道路 A*(390) 第一级 `NoPassClosedDoorsOrWater`（一切水硬不可走）经走廊**必然**成功（绕行是结构性必然，非贪心选择：涉水 ~576 成本远比绕行 ~3000+ 便宜，但第一级根本不涉水），路绕经河源头再大转弯（实测三叉河地图）。**修复**：河端点沿外法向**延伸到方形矩形边**——臂+方形边把地图真正分割成两半（原版语义），A* 无绕行路径只能涉水+铺桥；宽度/水深由原版深度场自然延伸（`GetTValue∈[0,1]` 覆盖走廊段），无人工水带无突变。配套 `GetDisplacedPoint` Postfix **压弯窗口**：端点外延后接缝处 tSeam≠0 → bell≠0 → 两侧独立噪声漂移 ±19-32 格，窗口把弯曲偏移乘 `clamp01((t-tSeamStart)/rise)×clamp01((tSeamEnd-t)/rise)`（tSeam=各边中点在线段投影）——走廊段直线、接缝处有效 bell=0（对齐保持）、图内深处原版行为。走廊水进 snapshot → `Convolve3x3` 跳过 IsWater 格（防混合带众数被卷成水）。

**能做程度**：
- ✅ 接缝穿越点对齐：Prefix `FindRoadExitCell` 强制返回接缝锚点 cell（已实现，含 angle 偏置免疫）。
- ✅ 接缝处方向大致连续：两端都以锚点为起/终点寻路。
- ✅ 接缝带内路面保留：IsRoad/bridge 地形判据 + paths±3 缓冲 + 接缝补铺（ApplyDistanceField Postfix）。
- ✅ 道路过河正常架桥：河端点延伸到方形边消除绕行走廊（桥由原版 Bridge 步骤在涉水处生成）。
- ❌ 接缝带宽以外路径重合：不能（两端独立寻路，成本地图不同）。

**兼容性**：只 patch `FindRoadExitCell`（private，AccessTools.Method 显式绑定）+ `ApplyDistanceField`（private）+ `Generate`（Postfix 只读快照），不碰 `Generate` 主逻辑。其他 mod patch 同方法时 Harmony 链正常叠加。

## E. 实测实现历程与最终方案（已完成基础设施 + 游戏内验证）

B-D 节是理论可行性分析。本节记录实际实现历程、踩过的坑、以及当前状态。

### E.1 噪声坐标方案：从球面回到平面（关键教训）

**尝试过的失败方案**：
1. **切平面一阶近似**（`anchor + first·offZ - second·offX`）：cell 格数直接乘切平面基。相邻 tile 切平面基方向不同（球面投影旋转）→ 跨 tile 错位 ~1.0 球面单位。
2. **球面三角形插值**（`CellToSphereExact`）：平面六边形顶点↔球面六边形顶点一一对应，重心坐标插值。理论上精确，实测仍错位 ~1.0——根因同上：相邻 tile 平面六边形各自独立投影，反推球面不对齐。
3. **球面坐标 + Perlin frequency 缩放**：把 sphere 坐标线性缩放到 cell 尺度。缩放不破坏连续性，但 sphere 坐标本身不连续（方案1/2的根因）。

**失败根因（通用）**：所有"cell→球面"的反向映射都假设相邻 tile 的平面坐标系可通过球面对齐。但 RimWorld 星球是球面多面体，相邻 tile 各自用自己中心的切平面基投影，两个平面坐标系之间有角度旋转（赤道→北极累积约 30°）。任何在 cell 层面做球面反推的方案都无法消除这个旋转。

**最终方案：全局平面坐标（tileOrigin）**。
- 核心：噪声采样和 void 裁切用**完全相同的坐标系**——cell 的平面坐标。void 已用平面坐标 + ComputeNeighborOffset 实现跨 tile 连续（接缝中点重合，误差 ≤ 重叠带）。噪声复用这套坐标。
- 实现：每个 tile 存 `tileOrigin`（全局平面位置）。锚点=(0,0)，地块=源 tileOrigin + ComputeNeighborOffset（生成时确定，序列化）。噪声采样坐标 = `cellLocal - center + tileOrigin`。
- **FixedSeed = WorldSeed 派生**：所有 tile 共享同一 Perlin 场（连续性要求），但 seed 不再是全局常量，而是 `HashCombineInt(WorldSeed, 13579)`（惰性计算）。这样不同世界种子生成不同 Perlin 场（地形随世界种子变化），同一世界的所有 tile 共享同一 Perlin 场（接缝连续）。
- 连续性证明：相邻 tile 共享边 cell 的采样坐标接近（同构于 void 的连续性），Perlin 在平面坐标连续 → 接缝连续。
- **关键认知**：Perlin 在任何连续坐标系里都连续，不限于球面。执着于"球面采样"是概念误区。

**实现文件**：
- `Source/TileProjection.cs`：`GetBasis`/`VertexToDir2D`（void 多边形投影用，唯一持有 GetTileCenter + GetTangentsToPlanet）。
- `Source/SeamlessNoiseProvider.cs`：`TryWarp`（全局平面坐标）+ `DiagnosticValue`（诊断条纹）。
- `Source/MapParent_SeamlessTile.cs`：`tileOrigin` 字段（序列化）。
- `Source/SeamlessTileManager.cs`：`GenerateTileMap` 算新 tile 的 tileOrigin。
- `Source/Patches_NoiseLeafWarp.cs`：patch Perlin/RidgedMultifractal GetValue，gate RimExodus 地块，`EnsureFixedSeed` 固定 seed 为 WorldSeed 派生值（`HashCombineInt(WorldSeed, 13579)`，惰性计算）——所有 tile 共享同一 Perlin 场（连续性），不同世界种子生成不同 Perlin 场（保留 WorldSeed 影响）。

### E.2 叶子层 patch 的覆盖边界（实测 + 调研确认）

叶子层 patch（`Patches_NoiseLeafWarp` patch `Perlin.GetValue`/`RidgedMultifractal.GetValue`）对**裸 Perlin** 有效，对**有组合器包裹的 Perlin** 失效。

**为什么组合器破坏叶子 patch**：组合器（Rotate/Scale/AddDisplacementNoise）在 Perlin 叶子**之前**对坐标做变换。patch 在叶子层 warp 坐标，但组合器在 warp 之后、Perlin 之前又对坐标做了 tile 特定的旋转/缩放，破坏了 warp 建立的全局对齐。

实测现象：沃土/沼泽/水体连续（fertility 是裸 Perlin），岩石形状/山体不连续（elevation 被 Rotate/Scale/AddDisplacementNoise 包裹）。

### E.3 genStep 数据来源分类（决定 patch 策略）

| 类型 | 说明 | 代表 genStep | 连续性 patch 策略 |
|---|---|---|---|
| **类型1：读静态 grid** | 读 `MapGenerator.Elevation/Fertility` | Terrain, RocksFromGrid(位置), RockChunks(位置), FindPlayerStartSpot | 在 GenStep_Terrain 前重写 grid |
| **类型2：自建噪声** | genStep 内 new Perlin 或读 RockNoises | ElevationFertility, RockNoises, TerrainPatchMaker, RockChunks(密度) | 裸 Perlin：叶子 patch 有效；有组合器：叶子 patch 失效 |
| **类型3：纯随机/配置** | Rand、biome、世界 tile 数据 | Roads, ScatterRuinsSimple, SteamGeysers, Animals, Snow, Fog | 本就离散，无需连续 |

**关键发现：Plants 没有自己的噪声**。Plants 读 `map.fertilityGrid` = `terrainGrid.TerrainAt(loc).fertility`（terrainDef 的字段），不读 `MapGenerator.Fertility` 静态 grid。所以 Plants 连续 ⟸ terrainDef 连续 ⟸ GenStep_Terrain 选择连续 ⟸ MapGenerator grid 连续。链条成立，无需单独 patch Plants。

### E.4 grid 重写方案（已废弃）

grid 重写（Prefix/Postfix GenStep_ElevationFertility 重写 Elevation grid）曾被视为解决 elevation 被 Rotate/Scale 包裹的方案。但分析后发现它本质是"逐 genStep 介入重写噪声"，维护成本高（要复制原版 elevation 的多层 Perlin + ScaleBias + Hilliness 系数等细节），与"避免逐 genStep patch"初衷冲突。

**放弃原因**：grid 重写虽然能解 elevation 连续性，但：
1. 要精确复制原版 elevation 的频率/缩放/Hilliness 系数，跟随版本维护。
2. 仍然只覆盖"读 grid"的 genStep，岩石种类（RockNoises 独立 Perlin）仍需单独处理。
3. 与接缝覆写方案（E.6）相比，侵入性更大、兼容性更差。

连续 Perlin 方案（含 grid 重写）整体已回退，代码保留在 `continuous-perlin` 分支。

### E.5 连续 Perlin 方案废弃（已回退）

连续 Perlin 方案（patch Perlin 叶子 + tileOrigin 全局平面坐标 + grid 重写尝试）整体废弃：
- 游戏内验证发现沃土/水体连续但岩石/山体不连续（elevation 被组合器包裹）。
- grid 重写虽可解但侵入性大。
- **转向接缝覆写方案（E.6）**：正常用原版噪声，只在接缝带做过渡。

回退操作：
- 删除连续 Perlin 相关代码（TileProjection/SeamlessNoiseProvider/Patches_NoiseLeafWarp/GenStep_DebugDirtWater/RimExodusDebug/NoiseGenType/debugDirtWaterMode）。
- 保留 tileOrigin 字段、void 体系、传送/邻居/预加载/边界带/分帧生成等已验证功能。
- 代码保留在 `continuous-perlin` 分支。

### E.6 接缝覆写 genStep — 卷积混合（已实现，游戏内验证通过）

**核心思想**：正常用原版噪声生成地形（各地块独立），只在接缝带做 terrainDef 过渡。不试图让噪声场全局连续，只保证接缝处视觉/通行连续。

**方案：备份基础地形 + 卷积混合**
1. 生成时 CoastalEdgeFill(230) 铺好海岸水后、void 裁切(1400) 前，备份完整 terrainGrid（baseTerrainSnapshot）。snapshot 记录含六边形外的海岸地形（供邻居 SeamOverride 卷积用）。
2. void 裁切正常做（六边形外铺 RimExodus_Void，但 snapshot 已保存裁切前状态）。
3. 新生成 tile C 完成后，接缝覆写 genStep(1410)：**混合带由 A snapshot 决定（非 C 的固定 bandWidth）**——候选 = 凡 aCell 在 A 矩形内、映射 `cCell = aCell + offset` 落在 C 六边形内的格（含 A 被 void 裁掉的条带格 + SeamOverlap 重叠带，见下），做 3×3 卷积混合。混合带宽度 = A 被裁掉的实际深度 + 重叠带，无固定配置。卷积加权（A 分布 × w + C 分布 × (1-w)），取众数写入 C。
4. **单向覆写**：只改 C，不改 A。

**混合带由 A snapshot 决定（关键设计修正）**：早期版本用 C 自身的 `bandWidth = seamOverrideRatio × mapSize × 0.5`（默认 31 格）从 C void 边界向内膨胀确定混合带。但 bandWidth=31 远超 A 实际裁切深度（~17 格），混合带深处映射到 A snapshot 取到的是 A 内部正常可见地形的混合——没有意义反而制造扭曲（岩石区域偶现硬过渡的根因）。修正后混合带完全由 A 的几何决定：A 被裁掉多少，C 就混合多少。

**为什么卷积**：terrainDef 离散不能直接加权平均。卷积把它变成"3×3 邻域的 terrainDef 分布"，分布可以加权平均，再取众数 → 平滑过渡。

**权重 w（逐格局部归一化，aCell 在本地 void 条带内的相对位置）**：`wBase = wCap × dSq/(dSq+dHex)`。dSq = aCell 到 A 方形边界的切比雪夫格距（解析 `min(x,z,S-1-x,S-1-z)`），dHex = aCell 到 A 六边形边的欧氏垂距。贴 A 六边形边（紧贴 A 可见区域）→ w≈wCap（强继承 A snapshot，代表性越强），贴方形外缘 → w≈0（弱继承）。逐格局部归一化还保证窄条带区段接缝侧 w 同样接近 wCap（连续性沿整条边一致，与条带深浅无关）。

**为什么弃用全局 maxDepth 归一（三代方案教训）**：第一代用全图 void 条带最大深度、第二代用"实际参与混合的候选集"最大深度归一 `wBase = wCap × (1 - clamp01(distToEdge_A/maxDepth))`——两者都被 A 方形角落格污染：角落深度可达 40-68 格（远超接缝边中点 ~17 格），且与接缝相邻的方形角落能绕过六边形顶点投影进 C 六边形的侧向楔形区（实测数据点 A(249,249)→C(59,146)，距 C 中心仅 ~69 格 ≪ 内切圆 ~108 格——第二代修复时"角落格投影到 C 后多在 C 六边形外被过滤"的假设被证伪），maxDepth 被抬高 2-3 倍 → 整条混合带 w≥0.45，众数投票里邻居只要 3×3 全一致就能压过分裂的 self 分布（ Granite 全带通吃，A 最外列 x=249 的深条带格也赢）。逐格比例无全局统计量，此类污染结构性不可能。dSq 切比雪夫 / dHex 欧氏的度量混用为有意取舍（≤√2 单调偏差，dither 下不可见）。已知保留行为：顶点楔形区仍参与混合（贴 A 六边形边的角落格 w≈wCap，与侧向邻居的混合顺序相关），不做走廊限制。

**权重噪声（dither 离散跳变）**：w 是纯线性距离函数时，GetMode 离散跳变在带内形成规则等距过渡线（像等高线）。在 w 上叠加低频空间 Perlin 噪声（`w' = clamp01(wBase + n×amp)`，n∈[-1,1]），把规则等距线打散成弯曲不规则斑块。基于 worldTile 稳定 seed（同一地块多次生成一致），幅度可配 `seamOverrideNoiseAmplitude`（默认 0.15，0=关闭）。

**为什么放在 Fog(1500) 之前**：让 `GenStep_Fog` 的 flood-fill 基于 void 裁切 + SeamOverride 覆写后的最终地形算可达性——void 外条带不可达→不揭雾，与渲染（void 透明）和寻路（void 不可通行）一致。MutatorFinal(1600) 多数 mutator 不写 terrainGrid（`TileMutatorWorker_Coast` 无 `GeneratePostFog` 重写、River 只建 lookup texture），但 AncientUplink/InsectMegahive 的 GeneratePostFog 会 SetTerrain——这些罕见任务地块上 SeamOverride 地形会被覆盖（已知小瑕疵）。

**兼容性**：不碰 grid/genStep 内部（除权重噪声自建的 Perlin），纯 terrainDef snapshot 操作。任何 mod 加的地形 genStep 都自动被备份+卷积覆盖。河流/海岸（mutator/TerrainPatchMaker）在备份时已含，卷积自然覆盖。
