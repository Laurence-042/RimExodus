# 第二阶段：最小技术原型

状态：已完成（矩形原型目标全部达成，后续能力由阶段 3/4/4a/5 接管）；生成与渲染验证已通过。

上级设计：[无缝世界地块探索](无缝世界地块探索.md)

## 阶段目标

使用矩形地图建立不依赖 VMF 渲染管线的最小原型，依次验证：

- 相邻 Pocket Map 的创建、销毁和宿主关联。
- 地图在宿主边界外的叠加显示。
- 宿主与相邻地图重叠带的稳定覆盖关系。
- 地图选取、移动命令和双向 Pawn 转移。
- 保存读档后恢复宿主与相邻地图关系。

本阶段不实现六边形裁切、连续地形、跨地图工作、寻路或射击（这些已升格为独立阶段 3/4/5，详见主设计文档）。

## 已完成的基础结构

- `MapParent_SeamlessTile` 继承原生 `PocketMapParent`，保存世界地块、方向、宿主偏移和相邻地块信息。
- `SeamlessTileManager` 负责生成、查找和移除相邻地图，并把 `sourceMap` 指向宿主地图。
- `SeamlessTileRegistry` 以宿主坐标返回所有可见相邻地图的矩形 footprint。
- `SeamlessMapUtility` 提供宿主坐标与相邻地图局部坐标之间的平移转换。
- `GenStep_SeamlessTile` 生成可辨识的矩形测试地形。
- Def、Mod 元数据和 net48 工程已可编译并输出到 `1.6/Assemblies/`。

方向编号为：0=北、1=东北、2=东南、3=南、4=西南、5=西北。当前仍是矩形原型，1/2 暂时共用东侧偏移，4/5 暂时共用西侧偏移。默认地图尺寸为 50×50，重叠带统一为 5 格。

## 生成与调试入口

`DebugActions_SeamlessTile` 提供六个方向的单独生成、`Generate All 6 Tile Maps` 和 `Remove All Tile Maps`。

宿主地图生成后会自动生成北侧相邻地图。这里有两个生命周期约束：

1. `MapGenerated()` 执行时 `MapGenerator.mapBeingGenerated` 仍非空，因此自动生成必须延迟到下一 tick。
2. `MapComponent` 会被自动安装到 Pocket Map；生成和 tick 钩子必须跳过 `map.IsPocketMap`，否则会递归生成口袋地图。

## 渲染问题与最终方案

### 被否决的实现

最初的渲染器在 `MapComponentDraw()` 中遍历所有 `SectionLayer`，直接调用 `Graphics.DrawMesh`，并尝试用正负高度 epsilon 控制宿主与相邻地图的覆盖关系。这个方案不可靠：

- `Graphics.DrawMesh` 的 CPU 提交顺序不等于不同 render queue 材质的 GPU 最终绘制顺序。
- Terrain 同时包含 opaque、transparent 等材质，高度微调不能统一决定所有像素的覆盖关系。
- 泛化重放 submesh 绕过了 `SectionLayer.DrawLayer()` 的专用语义。
- `SectionLayer_Watergen` 继承 `SectionLayer_Terrain`，但原版只应将它绘制到水深子相机；旧实现把它以 layer 0 送入主相机，产生蓝红水深调试色。

因此高度 epsilon 已删除，口袋地形保持原始 altitude。

### 主相机背景通道

`SeamlessTileRenderer` 现在维护专属 `CommandBuffer`，绑定到主相机的 `CameraEvent.BeforeForwardOpaque`：

1. 每帧清空并重建命令。
2. 只提交精确类型为 `SectionLayer_Terrain` 的主地形层；明确排除 Watergen、Lighting、Fog、Debug、Zone 等具有独立语义的层。
3. 按 `material.renderQueue` 升序稳定排序相邻地图内部的 terrain submesh。
4. 绘制完相邻地图颜色后只清深度、不清颜色。
5. 原版宿主地图随后正常绘制，从渲染阶段上保证 5 格重叠带由宿主覆盖。

相机变化时会从旧相机解除并绑定新相机；`MapRemoved()` 会移除并释放本 Mod 自己的缓冲区，不影响其他 Mod。

Pocket Map section 不处于宿主 `ViewRect`，因此 dirty section 仍需直接调用 `RegenerateAllLayers()`。该方法不会像 `TryUpdate` 一样清除 `dirtyFlags`，重建后必须手动清零，避免每帧重建全部网格。

## 裁剪平面与残影修复

原版宿主地图在四边绘制 500 单位宽的 `WorldClipper`。早期补丁只要某个 footprint 与一整块边缘平面相交，就取消整块平面。这会让 footprint 之外的屏幕像素失去本帧颜色写入；相机若只清深度，拖动画面时便会保留上一帧颜色，形成左上角或右上角残影。

`Patch_MapEdgeClipDrawer_DrawClippers` 现在执行精确矩形差集：

- 将原版四块裁剪平面表示为准确的世界矩形。
- 对每块平面依次减去所有相邻地图 footprint。
- 一次矩形相减最多生成上、下、左、右四块互不重叠的剩余矩形。
- 只绘制剩余矩形，并保持原版 `WorldClipper` 高度和世界对齐的纹理缩放、偏移。

这样只在真实 footprint 上开洞，其余边界外区域每帧仍由 clipper 写入颜色。

## 自动传送点与双向 Pawn 转移（已完成，可编译）

在生成相邻地块后，自动在接缝重叠带放置一对传送点，并实现 Pawn 走到传送点后双向无缝转移。

### 传送点 Thing

- `1.6/Defs/ThingDefs/SeamlessEnterSpot.xml` 定义 `RimExodus_SeamlessEnterSpot` ThingDef：
  - 继承 `BuildingBase`，`passability=Standable`、`pathCost=0`，Pawn 可正常走过。
  - 使用核心贴图 `Things/Building/Misc/DropBeacon`（1×1 信标，`Graphic_Single`），不依赖 VMF 资源。
  - 挂 `CompProperties_SeamlessTileEnterSpot`。

### 传送点组件（`CompSeamlessTileEnterSpot`）

- 入口端点不区分宿主侧或口袋侧，仅持有持久化的 `CounterpartSpot` 对端引用。
- 一对入口互相将对方设为 `CounterpartSpot`；传送目标直接取对端的 `Map` 和 `Position`。
- `direction`、`isHostSide`、`AdjacentTileParent`、`OwnTileParent` 等非对称入口状态已删除。

### 自动放置（`SeamlessTileManager.PlaceEnterSpots`）

- `GenerateTileMap` 生成口袋地图后自动调用 `PlaceEnterSpots`。
- 用 `ComputeEnterSpotHostCell` 计算重叠带中央的宿主坐标（避免紧贴地图边缘）。
- 本端传送点 `GenSpawn.Spawn` 到宿主地图；对端传送点经 `ToLocalCoord` 放到口袋地图对应局部坐标。
- 两个端点生成后建立双向 `CounterpartSpot` 引用。
- 关键：本端与对端传送点在宿主坐标（drawPos）上重合于同一 tile，因此 Pawn 转移后视觉位置不跳变。

### 双向转移触发（`SeamlessMapTransferTrigger`）

- 每张地图的组件每 30 tick 只扫描本地图入口，不依赖 `Find.CurrentMap`，也不跨地图遍历入口。
- `SeamlessMapTransfer.TryTransferPawn` 统一处理两个方向，直接把 Pawn 从当前入口转移到 `CounterpartSpot.Map/Position`。
- 每个地图组件持久化 `Dictionary<Pawn, Thing>` 到达锁。Pawn 仍站在刚抵达的入口上时阻止回弹；每 tick 检查一次，Pawn 一旦离开入口格立即删除锁，再次进入即可触发。
- 到达锁使用引用模式随存档保存；读档 `PostLoadInit` 会清理 Pawn、入口或地图关系失效的记录。

### 验证

- `dotnet build Source/RimExodus.csproj -c Debug` 通过（0 错误 0 警告）。
- 游戏内待验证：双向转移、离开即解锁，以及入口上保存/读档后到达锁继续生效。

## 相邻地块选中 + 跨地图移动指令（已完成，可编译）

在双向 Pawn 转移可用后，实现"选中渲染在宿主边界外的相邻地块上的对象，并命令 Pawn 通过传送点桥接跨地图移动"。

### 背景与范围（用户确认）

- 目标：让玩家能选中相邻地块（口袋地图）上的对象，并命令 Pawn 通过传送点桥接跨地图寻路移动。
- 选中：先做单击选中（对应 VMF `Patch_Selector_SelectableObjectsUnderMouse`），但反查工具设计成可被框选复用；框选、Zone 高亮、跳转/面板细节本次不做。
- 跨地图命令：本次只做移动（右键走过去），不做跨地图射击/近战（后续 Story）。
- 拓扑：只做单跳桥接（源地图 - 出口传送点 - 入口传送点 - 目的地图），不做 VMF 式 `AStar<MapTraverse>` 多跳地图图——因为最终成品里一张地图最多只能看到六个邻居的边界附近，天然不需要多跳。
- 视觉反馈：先保证能选中并下达指令，UI 细节（跳转高亮等）后续再打磨。

### 架构决策

深入读 VMF 的 `Patches_FloatMenu.cs`/`Patches_Job.cs`/`Patches_Designator.cs`/`Patches_GUI.cs` 后发现，VMF 没有用"检测到跨图就绕开 FloatMenu 直接下 Goto 单"的简化方案，而是做了一套"环境态地图上下文自动替换"，让整条原版链路（FloatMenuOptionProvider 全家桶 + JobDriver + Designator）在鼠标/目标落在车辆地图上时自动透明切换到正确的 Map+坐标。

**用户已确认**：阶段 2 改用这种"环境态地图上下文替换"架构。理由：覆盖面更广（未来加攻击/搬运/建造时不需要逐个重做），且是 VMF 验证过的成熟模式。

**但仍保留的简化**（结合本仓库单跳约束）：
- 不需要 VMF 式 `CrossMapReachabilityUtility`（地图图 + `AStar<MapTraverse>` + `Reachability.CanReach` 深度 patch）。单跳场景下，"走到桥接传送点 → 现有 `SeamlessMapTransferTrigger` 自动完成实际转移 → 到达后续下一段 Goto" 的两段式已经足够。
- 不需要 `JobDriverAcrossMaps`/`ToilsAcrossMaps` 那种"单个 Job 内部跨图行走 + drawOffset 视觉过渡"的复杂 JobDriver；两段式 Job（先 Goto 传送点，再 Goto 最终格）在单跳场景下视觉上已经连续（重叠带传送点坐标重合）。
- `Patch_Designator_SelectedUpdate` 式"每帧环境态"和 `Patch_JobDriver_Map` 式"Toil 内 this.Map 跟随目标"本阶段不做（建造/Designator 跨图不在本次范围内）。

**关键架构结论**：`RimWorld.FloatMenuMakerMap.GetOptions` 在最开头硬编码 `clickPos.InBounds(Find.CurrentMap)` 与 `new FloatMenuContext(selectedPawns, clickPos, Find.CurrentMap)`。这意味着点击宿主边界外（口袋地图 footprint 内）的格子会在第一行 `InBounds` 检查就被拒绝；且 Pawn 已跨图到口袋地图上时，只要玩家仍在宿主视角（`Find.CurrentMap` 恒为宿主），该 Pawn 也收不到右键指令。VMF 通过"聚焦车辆地图"（`Command_FocusVehicleMap`，切换 `Find.CurrentMap` 语义）解决；本项目按用户既定方向（不做视角聚焦切换，只在宿主视角里"peek"邻居）不采用这条路，而是做一个独立的、绕开 FloatMenuMakerMap 主流程的"移动指令"直通通道。

### 设计

**阶段 0：共享坐标反查工具**
- `SeamlessTileRegistry.TryGetPocketMapAtHostCell(Map host, IntVec3 hostCell, out MapParent_SeamlessTile parent)`：遍历 `Find.World.pocketMaps` 中 `sourceMap == host` 的 `MapParent_SeamlessTile`，用 `ToLocalCoord` + `InBounds` 判断命中。
- `SeamlessMapUtility.TryResolveMapPosition(Vector3 mouseMapPosition, Map hostMap, out Map targetMap, out IntVec3 targetLocalCell)`：命中口袋地图则返回其 Map + 局部坐标；否则返回宿主地图自身。供阶段 1（选中）和阶段 2（移动指令）共用；未来框选可直接复用同一反查。

**阶段 1：单击选中相邻地块上的对象**
- `Patches_Selector.cs`：Prefix `Selector.SelectableObjectsUnderMouse`。用阶段 0 工具解析鼠标位置；命中口袋地图则在该 Map 上收集可选对象（`SeamlessGenUI.ThingsUnderMouse`，Map 感知版），否则 `return true` 走原版。`__result = 收集结果; return !__result.Any();`（命中为空时仍回退原版，保证宿主地图自身选中不受影响）。

**阶段 2：跨地图移动指令**
- 前端：`Patches_FloatMenuMakerMap.cs` Prefix 全量接管 `FloatMenuMakerMap.GetOptions`。两端都在宿主地图时 `return true` 完全放行原版；否则复制原方法逻辑（构造 `FloatMenuContext`、`ShouldGenerateFloatMenuForPawnCrossMap` 放宽版、通过反射调用私有的 `GetProviderOptions`），并逐 Pawn 记录 `SeamlessCrossMapOrders.RecordPendingTarget`（只要 `pawn.Map != context.map` 就记录，覆盖宿主→口袋和口袋→宿主两个方向）。
- 后端：`Patches_Job.cs` Prefix `Pawn_JobTracker.StartJob`，调用 `SeamlessCrossMapOrders.TryInterceptJob`。检测到跨图 Job 时不让原始 Job 执行，转而调用桥接逻辑：在 `pawn.Map` 上找到 `CounterpartSpot.Map == targetMap` 的 `CompSeamlessTileEnterSpot`，校验可达性，下发 `JobDefOf.Goto` 走到桥接点（复用已验证的 `SeamlessMapTransferTrigger` 自动完成转移），在 `SeamlessCrossMapPendingDestinations` 登记"到达 targetMap 后继续走到 targetLocalCell"。转移成功后 `SeamlessMapTransferTrigger` 消费续程登记并自动续发 Goto。
- 这一个拦截点可以覆盖任何来源的跨图 Job（不止右键菜单），为将来扩展攻击/搬运留了口子。

### 编码阶段发现的关键事实（与计划书描述有出入，以此为准）

1. **`FloatMenuContext` 构造器内部两次调用 `GenUI.ThingsUnderMouse` 时完全不接收 Map 参数**（隐式操作 Find.CurrentMap），且 `FloatMenuMakerMap.GetOptions` 开头/中间三处都是字面 `Find.CurrentMap` 属性访问。这使得 VMF 那种"精确 Transpiler 替换单个调用点"的方式意义不大（IL 结构需逐版本核对，没有把握每次游戏更新都稳定命中），因此最终选择更稳妥的 **Prefix 全量接管**（复制原方法体逻辑，只在跨地图场景生效）。两端都在宿主地图的最常见场景完全走原版代码路径，不受影响。
2. **`Selector.SelectInternal` 会在 `map != Find.CurrentMap` 时自动 `Current.Game.CurrentMap = map` 并跳转镜头**——选中相邻地块上的 Thing 会自动切换视角/跳镜头到该地图（原版处理跨地图选中的方式）。~~采用推荐方案：**接受这个自动切视角行为**，不额外 patch 抑制。~~ **已修复**（见下文"选中跨图 Pawn 的无感相机覆盖"章节）：现对 `SelectInternal` 加 Prefix+Postfix，切图后用无感偏移覆盖原生聚焦，保持相机相对位置不变。
3. **`FloatMenuOptionProvider_DraftedMove.GetSingleOption` 只对 `Drafted` pawn 生效**（`Undrafted => false`），且实际调用的 `gotoLoc` 是 `RCellFinder.BestOrderedGotoDestNear` 计算出来的"附近可站立格"，**不一定等于原始点击格**。因此 `SeamlessCrossMapOrders.TryInterceptJob` 不能按 Cell 精确匹配 pending 记录，改为"只要该 Pawn 有跨地图 pending 记录，且这是紧随其后的下一个 `JobDefOf.Goto`，就当作同一次指令"。
4. **`Pawn_JobTracker.TryTakeOrderedJob` 并不直接调用 `StartJob`**：它先调用 `job.TryMakePreToilReservations`（对 `JobDriver_Goto` 而言就是 `pawn.Map.pawnDestinationReservationManager.Reserve`，**用 pawn.Map 的 reservation grid 保留了一个实际上属于另一张地图坐标系的 Cell 值**），然后把 Job 放进 `jobQueue`，真正的 `StartJob` 是之后通过 `CheckForJobOverride`/`TryFindAndStartJob` 从队列取出时才发生的。我们的 Prefix 挂在 `StartJob` 上时序仍然正确（能在原始跨图 Job 真正开始执行前拦截替换），但会在 `pawn.Map` 上留下一个此次从未真正使用、也从未被显式释放的"目的地格子"预定占用。这是一个**已知的小缺陷**（大概率只是暂时占用宿主地图上一个不相关格子的"目标地预定"，不会崩溃），本次不修复，记录以便后续需要时处理（例如在 `Patches_Job.cs` Prefix 里识别到跨图后主动调用相应的 `ReleaseAllOwnedBy`/`Reserve` 撤销 API）。

### 补充修复：口袋地图上的 Pawn 之前不可见（已修复）

- **问题**：`SeamlessTileRenderer` 之前只重放口袋地图的 `SectionLayer_Terrain`（地形），完全没有绘制 Pawn/建筑等动态物体。原版 `DynamicDrawManager.DrawDynamicThings()` 只在 `Find.CurrentMap == 该地图` 时才会绘制该地图上的动态物体，所以聚焦宿主地图时，口袋地图上的 Pawn 从未被绘制过，自然也无法被鼠标选中（选中反查逻辑本身没问题，只是画面上根本没有东西可点）。
- **修复**：`SeamlessTileRenderer.DrawPocketMapPawns` 在 `MapComponentDraw()` 里对每个口袋地图，遍历 `pocketMap.mapPawns.AllPawnsSpawned`，直接调用 `pawn.DrawNowAt(pawn.DrawPos + parent.hostOffset.ToVector3())`。
  - `Thing.DrawNowAt(Vector3 drawLoc)` 是引擎自带的公共方法，接受显式坐标、绕开 `DrawPos`/`Position`，`Pawn` 重写的 `DynamicDrawPhaseAt` 会把这个显式坐标一路传给 `PawnRenderer`，因此**不需要 patch `Thing.DrawPos`/`Pawn_DrawTracker.DrawPos` 这种大范围侵入式 patch**（那是 VMF 的做法，但 `DrawPos` 在全局被大量非渲染逻辑读取，全局 patch 风险高）。
  - 只处理了 Pawn；建筑/物品的 GUI 悬浮图标（`ThingOverlays.ThingOverlaysOnGUI`，血条/情绪图标等）仍未做偏移处理，如果后续需要可以参照 VMF 的 `Patch_ThingOverlays_ThingOverlaysOnGUI` 补充。
  - 每个 Pawn 绘制包了 try/catch + `Log.ErrorOnce`，避免单个 Pawn 绘制异常导致整帧渲染中断。

### 补充修复：重叠带内宿主自身格子被误判为口袋地图（已修复）

- **问题**：命令 Pawn 走向宿主地图北缘格（如 `125,0,247`）时，Pawn 会穿过传送带跨图到地图 B 的 `125,0,2`。宿主地图 250×250（格 0–249），北侧口袋地图 `hostOffset=(0,0,245)`，因此宿主格 `125,0,247` 反查为口袋局部 `125,0,2`——正是用户报告的坐标。
- **根因**：`SeamlessMapUtility.TryResolveMapPosition` 把**任何**落在口袋地图 footprint 内的宿主格都解析为口袋地图，即使该格仍在宿主地图自身边界内。
- **修复（第一版，已废弃）**：开头先判断 `hostCell.InBounds(hostMap)`，命中则直接归属宿主地图。但这只是"宿主边界内一律归宿主"的刚性规则，无法表达六边形方案里"重叠带内按最近中心决定归属"的语义。
- **修复（最终版，采用六边形最近中心所有权规则）**：`SeamlessTileRegistry.TryGetOwnerPocketMap` 用最近中心规则决定归属——候选 = 宿主地图中心 + 所有 footprint 覆盖该格的锚定口袋地图中心，取距离最近的格子中心作为逻辑所有者。`TryResolveMapPosition` 调用它，命中口袋地图则返回其 Map + 局部坐标，否则归属宿主。
  - 北缘边界：宿主中心 z=125，北侧口袋中心 z=370，两者中点 z=247.5。因此 `125,0,247` 距宿主更近 → 留在地图 A；`125,0,248`/`125,0,249` 距口袋更近 → 传送到地图 B。与用户要求一致。
  - 该规则与 `doc/用可重叠正方形承载六边形网格的空间映射方案.md` 的最近中心 Voronoi 所有权模型一致，为后续六边形裁切/连续地形铺路。
- **验证**：`dotnet build` 通过（0 错误 0 警告）；北缘归属边界经计算确认在 z=247.5。

## 第二阶段细节修复三则（已完成，可编译，游戏内待验证）

### 修复 1：选中跨图 Pawn 的无感相机覆盖

- **问题**：在地图 A 点击地图 B 的 Pawn 时，原生 `Selector.SelectInternal`（`references/.../RimWorld/Selector.cs:379-384`）会先 `Current.Game.CurrentMap = map`（行 381）再 `Find.CameraDriver.JumpToCurrentMapLoc(thing.PositionHeld)`（行 384）硬跳到该 Pawn 上。玩家体验是"切图 + 镜头猛地聚焦到选中 Pawn"，而期望是"切图但相机保持相对偏移，看上去还在看接缝附近的同一位置"。
- **方案**：对 `Selector.SelectInternal` 加 Prefix + Postfix（`Patches_Selector.cs` 的 `Patch_Selector_SelectInternal`）。
  - **Prefix**：原方法执行前（此时 `Find.CurrentMap` 还没切）检测即将选中的 `obj` 是 Thing 且 `thing.MapHeld != Find.CurrentMap` 且两者是直接邻居（`SeamlessCameraFocus.FindNeighborOffset` 返回非 null）→ 记录 `preservedCamPos = Find.CameraDriver.MapPosition.ToVector3()` 和 `crossMapOffset` 到静态字段。原方法照常执行（不 `return false`）。
  - **Postfix**：若 Prefix 记录了上下文，用 `Find.CameraDriver.JumpToCurrentMapLoc(preservedCamPos - crossMapOffset)` 覆盖行 384 的聚焦。末尾清空静态字段避免影响后续同地图选中。
  - **复用**：`SeamlessCameraFocus.FindNeighborOffset` 从 `private` 提为 `internal`，供"自动到达聚焦"和"选中切换"两条路径共用。无感算法（`targetPos = camPos - offset`）与 `SeamlessCameraFocus.TryAutoFocusOnArrival` 完全一致。
  - **边界**：若选中目标不是直接邻居（offset 查不到），不记录不覆盖，保持原生聚焦行为。
- **风险**：Postfix 覆盖发生在行 384 之后；`JumpToCurrentMapLoc` 是同步设 `rootPos`（无异步），在 Postfix 调用时已稳定，安全。原方法行 382 的 `PlayOneShotOnCamera` 和行 392 的 `SelectionDrawer.Notify_Selected` 不影响相机位置，无需处理。

### 修复 2：传送点载体从 Building 改为 Ethereal（ThingWithComps）

- **问题**：传送点用 `Building` category（继承 `BuildingBase`），可被攻击/拆除、可被 AI 占领、`isEdifice` 默认 true 会与岩山墙冲突、且 `PlaceEnterSpots` 的 `Walkable` 过滤主动跳过岩山/深水格。
- **方案（Ethereal 载体）**：改 `1.6/Defs/ThingDefs/SeamlessEnterSpot.xml`：
  - `thingClass`：`Building` → `ThingWithComps`；`category`：`Building` → `Ethereal`。
  - 加 `destroyable=false`、`useHitPoints=false`、`selectable=false`、`drawerType=None`。
  - 保留 `passability=Standable`、`pathCost=0`、`altitudeLayer=FloorEmplacement`、`size=(1,1)`、`comps`。删除 `graphicData`（`drawerType=None` 不绘制）。
- **关键验证结论**（均在 `references/RimWorldDecompiled/` 反编译源确认）：
  - **Ethereal 进 `listerThings`**：`ListerThings.EverListable`（`Verse/ListerThings.cs:298-309`）只排除 `Mote`（和 Region 级 `Projectile`），Ethereal 返回 true → `ThingsOfDef` 照常 O(1) 工作。消费者（`SeamlessMapTransferTrigger`/`SeamlessCrossMapOrders`）零改动。
  - **不会被攻击**：`AttackTargetFinder` 按 `IAttackTarget` 接口查（`ThingRequestGroup.AttackTarget`），与 category 无关；传送点不实现该接口。
  - **不会被占领**：`ThingDef.Claimable`（`ThingDef.cs:688`）要求 `building != null && building.claimable`；Ethereal 无 `<building>` 节点，`building == null` → 不可占领。
  - **不进 edificeGrid、可与岩山墙共存**：`IsEdifice()`（`Verse/EdificeUtility.cs:5`）读 `building.isEdifice`；Ethereal 无 building 字段 → 不是 edifice。`GenSpawn.SpawningWipes`（`Verse/GenSpawn.cs:449`）的 edifice 冲突擦除只在"新生成物 IsEdifice()"时触发，Ethereal 跳过整块 → 不会擦除已有岩山墙。
  - **`drawerType=None` 必须**：`selectable=false` 不跳过绘制（`DynamicDrawManager.RegisterDrawable` 只看 `drawerType`，`Verse/DynamicDrawManager.cs:158`）；默认 `RealtimeOnly` 会用 `BadGraphic`（粉色缺失贴图）每帧绘制。原版 `Ethereal_Various.xml` 的 `EtherealThingBase` 正是 `category=Ethereal + drawerType=None` 的标准模式。
  - **`destroyable=false` 后清理用 `DeSpawn`**：`Thing.Destroy`（`Verse/Thing.cs:1045`）在 `!def.destroyable` 时直接 return（不 DeSpawn、不移除注册），所以 `PlaceEnterSpots` 失败回退从 `Destroy()` 改为 `DeSpawn()`。正常卸载走 `RemoveTileMap → DeinitAndRemoveMap`（整张地图销毁），不调单 Thing Destroy，不受影响。
- **放置过滤放宽**（`SeamlessTileManager.cs` `PlaceEnterSpots`）：
  - 源端去掉 `Walkable` 过滤（Ethereal 可与任何地形共存）。
  - 对端保留 `Walkable` 过滤——但语义从"放置可行性"改为"传送可行性"：对端不可站立意味着 Pawn 落地格（`TryTransferPawn` 第 51 行也校验 `arrivalCell.Walkable`）无法使用，该对传送点永远无法触发，直接跳过不铺。
- **消费者零改动**：`SeamlessMapTransferTrigger`、`SeamlessCrossMapOrders`、`SeamlessMapTransfer` 都用 `ThingsOfDef` + `TryGetComp` + `Position`/`Map`/`Spawned`，与 category 无关。

### 修复 3：传送反弹 bug（pawn 级锁 + 离开接缝带才解锁）

- **问题**：传送点沿接缝满铺，Pawn 被传到对端 B_x 后，续程 Goto 沿接缝前进，离开 B_x 即解锁（旧 `PurgeInvalidArrivalLocks` 判定 `pawn.Position != arrivalSpot.Position`），踩上相邻 B_{x+1}（无锁）又被传回，寻路终止。
- **根因**：旧 `arrivalLocks: Dictionary<Pawn, Thing>` 锁的是"特定 spot 对象"，`IsArrivalLocked(pawn, thing)` 比较 `arrivalSpot == currentSpot`。Pawn 离开到达的那个 spot 就解锁，防不住"沿接缝走到相邻 spot"。
- **方案（pawn 级锁 + 离开接缝带解锁）**：把锁语义从"锁特定 spot"升级为"锁 Pawn 的跨图到达状态"（`SeamlessMapTransferTrigger.cs`）：
  - `arrivalLocks` 类型：`Dictionary<Pawn, Thing>` → `Dictionary<Pawn, bool>`（Pawn 级锁状态）。
  - `RecordArrival(pawn)`：只记 Pawn（不再记 spot），设 `arrivalLocks[pawn] = true`。`SeamlessMapTransfer.TryTransferPawn` 调用处同步改为单参数。
  - `IsArrivalLocked(Pawn pawn)`：返回 `arrivalLocks.ContainsKey(pawn)`。Pawn 在锁状态时，踩**任何**接缝 spot 都被锁住（`CheckLocalEnterSpots` 过滤条件）。
  - `PurgeInvalidArrivalLocks`：清除条件从"离开特定 spot"改为"不再站在本图任何接缝传送点上"。实现：每帧收集本图所有接缝传送点位置到 `HashSet<IntVec3>`，遍历已锁 Pawn 检查 `seamPositions.Contains(pawn.Position)`；不在任何接缝 spot 上（已离开接缝带）或 Pawn 失效（destroyed/dead/despawned/不在本图）则移除锁。
  - `ExposeData`：value `LookMode` 从 `Reference` 改为 `Value`。
- **性能**：已锁 Pawn 通常 1-3 个（刚跨图的），接缝 spot 数 ≈ 接缝长度（~96）。每帧 `PurgeInvalidArrivalLocks` 开销 ≈ O(seamSpots) 建 HashSet + O(lockedPawns) 查询，可忽略。
- **设计取舍**：考虑过"额外铺第二层 unlock spot Thing"（踩上才解锁），验证表明它逻辑上等价于"用现有接缝 spot 判定 Pawn 是否还在接缝带"，但多一倍 Thing 注册/绘制/存档开销且边界易卡死，故采用更轻的"复用现有接缝 spot 集合"方案。考虑过"pawn 级时间冷却"（tick 计数器），更轻但语义是时间窗而非空间，最终选空间锁以匹配"离开接缝带"的直觉语义。

### 修复 4：跨图切换相机缩放不一致

- **问题**：选中跨图 Pawn 或自动聚焦切图后，相机缩放（zoom）会变成新地块记忆的值（通常新地块默认 24f），而不是保持玩家当前的缩放。
- **根因**：`Current.Game.CurrentMap` setter 触发 `MapInterface.Notify_SwitchedMap`（`RimWorld/MapInterface.cs:211-212`），后者用 `Find.CameraDriver.SetRootPosAndSize(rememberedCameraPos.rootPos, rememberedCameraPos.rootSize)` 从**新地图**的 `rememberedCameraPos` **同时恢复位置和缩放**。每张 Map 各存一份 `RememberedCameraPos`（`Verse/Map.cs:217`，默认 `rootSize=24f`）。我们原先只用 `JumpToCurrentMapLoc(targetPos)` 恢复位置（`CameraDriver.cs:540-543` 只设 `rootPos.x/z`，不碰缩放），所以缩放被原生恢复值覆盖。
- **修复**：切图前同时记录 `camSize = Find.CameraDriver.RootSize`，切图后改用 `SetRootPosAndSize(new Vector3(targetPos.x, 0f, targetPos.z), camSize)`（与原生 `Notify_SwitchedMap` 同一方法）同时恢复位置和缩放。
  - `SeamlessCameraFocus.TryAutoFocusOnArrival`：记录 camSize，切图后 `SetRootPosAndSize`。
  - `Patches_Selector.cs` 的 `Patch_Selector_SelectInternal`：Prefix 增记 `preservedCamSize`，Postfix 改用 `SetRootPosAndSize`。
  - 无需手动写 `arrivalMap.rememberedCameraPos`：`SetRootPosAndSize` 后，`CameraDriver.CameraUpdater`（`CameraDriver.cs:427-432`）每帧自动把新 `rootPos`/`RootSize` 镜像回 `CurrentMap.rememberedCameraPos`。
  - 传 `new Vector3(targetPos.x, 0f, targetPos.z)`：`SetRootPosAndSize` 直接赋值给字段，但 `ApplyPositionToGameObject`（`CameraDriver.cs:436-450`）会自己重算 y，传 0 安全。

### 修复 5：过传送点卡一下（轮询间隔 + GC 分配）

- **问题**：Pawn 走到传送点上后会"停顿一下"再被传送。
- **根因**：`SeamlessMapTransferTrigger.ScanIntervalTicks` 原为 30（约 0.5 秒）。触发是轮询式的——Pawn 到达传送点后 Goto job 已结束（到达目标格），但没有任何事件触发，只能等下一次 30-tick 扫描窗口。平均 15 tick（~0.25s）、最坏 30 tick（~0.5s）的停顿感即源于此。续程 Goto 在转移同 tick 内 `StartJob`，无延迟。
- **修复**：`ScanIntervalTicks` 改为 1（每 tick 扫描），消除停顿。
  - **性能优化**（配合每 tick 扫描）：
    - `cachedEnterSpotDef` 字段缓存 Def，避免每 tick `DefDatabase.GetNamedSilentFail`。
    - 用 `static readonly List<Thing>/List<Pawn>/HashSet<IntVec3>` 复用列表替代每 tick `new List` 快照（`CheckLocalEnterSpots` 和 `PurgeInvalidArrivalLocks` 都改 Clear+Add），消除每 tick GC 分配。
    - `PurgeInvalidArrivalLocks` 在 `arrivalLocks.Count == 0` 时立即 return（空操作），绝大多数 tick 无开销。
  - 开销评估：每 tick `ThingsOfDef`（O(1) 取 list）+ 接缝满铺（~96 spot）× 少量 pawn 的位置比较，开销极低。



**核心架构转变**：从"宿主特殊论"（依赖 `sourceMap`/`IsPocketMap` 区分宿主与口袋）转向"地块对等论"（基于直接邻居表）。目的是支持核心交互场景里的 B→C（口袋到口袋），使 A→B、B→A、B→C 完全相同处理。详细架构事实见 `AGENTS.md` 的"当前架构核心事实（地块对等论）"章节。

### 关键改动
- **直接邻居表**：`MapParent_SeamlessTile.neighbors`（`List<NeighborLink>`，每条 `{direction, neighbor, offset}`）。偏移契约 = 邻居本地 → 本地块坐标的平移。锚点 A 的邻居表存于 `SeamlessTileManager`，口袋的存于 `MapParent_SeamlessTile`，由 `SeamlessTileGraph` 统一查询。
- **sourceMap 扁平化**：所有地块 sourceMap 指向锚点 A，避免原生嵌套副作用。
- **传送点满铺**：`PlaceEnterSpots` 沿接缝方向遍历每个可通行格放一对传送点（载体为 Ethereal/ThingWithComps，见"修复 2"）。多点寻路 `TryFindNearestReachableBridgeSpot` 选最近可达。
- **自动聚焦**：首个殖民者入新地块触发 `SeamlessCameraFocus.TryAutoFocusOnArrival`，切换 CurrentMap + 无感相机（硬跳覆盖）。
- **对称渲染**：`SeamlessTileRenderer` 遍历邻居画 Terrain + ThingsGeneral + Pawn。重叠带覆盖暂为"聚焦者覆盖"，完全对称留待连续地形阶段的归属裁剪。
