# 重构跨地图转移：征召状态的标准实现

## 问题根因
`draftedInt` 本身在 `TryTransferPawn` 里已正确恢复，但用户仍看到征召丢失。根因有两个：

1. **`pawn.lord` 跨图后悬空**：`Pawn.DeSpawn` 不清 `lord` 字段，跨图后 pawn 仍指向 B 的旧 lord。`Pawn.GetGizmos` 里 `GetLord()?.AllowsDrafting(this)` 走旧 lord 判定，如果旧 lord 的 LordJob 禁止征召，征召 gizmo 被禁用——用户看到的是"征召按钮灰了/不可用"，误以为征召丢了。旧 lord 的残留状态也可能干扰 think tree。

2. **`mindState.Reset` 时序错误**：在 `Drafted = true` 恢复之后执行，清掉了 duty/priorityWork。这行是从旧代码抄来的，在引入 drafted 恢复后多余且有害。

## 重构方案：TryTransferPawn 里收敛为唯一标准实现

调研确认 `TryTransferPawn` 是 RimExodus 中**唯一**的 pawn 跨图转移入口（没有旁路）。所以只需把这一处的"状态保存 → DeSpawn → Spawn → 状态恢复"整理成正确的时序。

### 修改 `Source/SeamlessMapTransfer.cs` 的 `TryTransferPawn`

**转移前保存**（DeSpawn 之前）：
- `wasDrafted = pawn.drafter?.Drafted ?? false`
- `wasFireAtWill = pawn.drafter?.FireAtWill ?? true`
- 保存旧 lord 引用并正确 detach：`var prevLord = pawn.GetLord(); prevLord?.Notify_PawnLost(pawn, PawnLostCondition.Vanished);`

**转移**（DeSpawn → Spawn，中间 drafter 被销毁并重建）：
- `pawn.DeSpawn()` — drafter 被置 null，curJob 被 StopAll 清空
- `GenSpawn.Spawn(pawn, arrivalCell, arrivalMap, rotation)` — 新 drafter 实例（draftedInt=false）

**转移后恢复**（Spawn 之后）：
- 恢复征召：`if (wasDrafted) pawn.drafter.Drafted = true`（setter 会清队列+EndCurrentJob，所以必须在续程 StartJob 之前）
- 恢复 fireAtWill：`pawn.drafter.FireAtWill = wasFireAtWill`
- 确保 lord 字段干净：`pawn.lord = null`（Spawn 不清它，旧 lord 已在 DeSpawn 前 Notify_PawnLost，这里确保字段本身为 null，避免 GetGizmos 的 AllowsDrafting 走旧 lord）

**删除多余操作**：
- 删除 `pawn.jobs?.EndCurrentJob(...)` — DeSpawn 已 StopAll，curJob 已经是 null，这行无操作
- 删除 `pawn.mindState?.Reset(...)` — 时序错误（在 Drafted 恢复后清 duty/priorityWork），且 DeSpawn 已 StopAll，不需要额外 mindState 清理。如果确实需要清 mentalState（防止跨图后残留精神状态），改为只调 `pawn.mindState?.mentalStateHandler?.Reset()` 而非全量 Reset，且放在恢复之前

### 为什么这是"唯一标准实现"
- `TryTransferPawn` 是所有跨图转移（A→B、B→A、B→C）的唯一入口
- 征召/lord 状态保存与恢复完全内聚在这个方法里
- 上层调用者（`CheckLocalEnterSpots`）不需关心状态恢复，只需在 `TryTransferPawn` 返回 true 后做续程
